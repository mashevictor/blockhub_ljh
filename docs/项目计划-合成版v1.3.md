## 0. 架构与 Web/Flutter 解耦设计（契约驱动）

**核心原则**：后端只产出两份契约——`page_schema`（UI 树）与 `capability_manifest`（包清单），二者都由同一份能力注册表派生。Web（runtime-web）与 Flutter（runtime-app）各自实现 Widget 注册表，按 `capability_key` 渲染，**互不依赖对方代码**。

| 层 | 内容 | 现状 |
|---|---|---|
| ① 单一能力源 | `backend/app/data/capability_registry.py` → `ALL_CAPABILITIES`（含 `widget/web_pkg/flutter_pkg/route/agent_id`） | 已落地 |
| ② 契约生成 | `schema_generator.py`（keys→page_schema）、`build_manifest.py`（keys→包清单：web=`@blockhub/web-capability-{slug}`，flutter=`capability_{key}`）、`GET /runtime/{id}/schema|manifest` | 已落地 |
| ③ Web 端 | `packages/web-core` WidgetHost + **13** 个解耦包 | 已落地 |
| ④ Flutter 端 | `runtime-app` WidgetRegistry + CAPABILITY_KEYS 菜单裁剪 + per-app APK | 已落地（物理 Melos 拆包 GA 后） |

**解耦红线**：① 后端永不直接写死某端 UI，必须经 schema+manifest；② Web/Flutter 不共享实现文件，只共享契约（schema 同构定义 + manifest JSON）；③ 新增能力时两端可独立排期、独立验收；④ W3 收口项（manifest 动态加载 + codegen TS/Dart）把契约固化为两端类型，防止长期漂移。
