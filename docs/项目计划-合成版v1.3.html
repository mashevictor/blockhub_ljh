四、项目架构与 Web/Flutter 解耦设计（契约驱动）

核心原则：后端只产出两份契约——page_schema（UI 树）与 capability_manifest（包清单），二者都由同一份能力注册表派生。 Web（runtime-web）与 Flutter（runtime-app）各自实现 Widget 注册表，按 capability_key 渲染，互不依赖对方代码。 新增一个能力 = 1 条注册表条目 + 1 个 web-capability 包 + 1 个 Flutter Widget，全程零跨端耦合。

① 单一能力源（后端 · 已落地）

  • backend/app/data/capability_registry.py → ALL_CAPABILITIES
  • 每条能力含：widget · web_pkg · flutter_pkg · route · agent_id
  • 36 Capability 入库即注册，是全部 UI 的唯一真相源

② 契约生成（后端 · 已落地）

  • schema_generator.py：capability_keys → page_schema JSON（menu + schema node，type=widget 小写）
  • build_manifest.py：capability_keys → 包清单（web: @blockhub/web-capability-{slug}；flutter: capability_{key}）
  • GET /runtime/{id}/schema|manifest 两端共用

③ Web 端（runtime-web · 已落地）

  • packages/web-core WidgetHost 按 capability_key 渲染
  • 5 个解耦包：web-capability-chat / approval / dashboard / kb / voice
  • 每包独立注册 Widget，物理包可 manifest 按需裁剪

④ Flutter 端（runtime-app · 待 W5 对齐）

  • runtime-app/lib：services / config / models / pages
  • 自建 WidgetRegistry，按同一 capability_key 映射
  • Dio+SSE 拉同一 schema/manifest，与 Web 共用 appId
解耦边界红线（两端必须遵守）：
  • 后端永不直接写死某端 UI；所有 UI 必须经由 page_schema + manifest。
  • Web 与 Flutter 不共享实现文件；只共享契约（schema.ts 同构定义 + manifest JSON）。
  • 新增能力时，Web 包与 Flutter Widget 可独立排期、独立验收，互不阻塞。
  • W3 收口项"manifest 动态加载 + codegen TS/Dart"正是把这份契约固化成两端类型，确保长期解耦不漂移。
