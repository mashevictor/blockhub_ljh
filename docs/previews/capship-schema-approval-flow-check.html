1. 截图暴露的问题（为何觉得「没同步」）

现象：聊天区已写「管理员已直接发布，正式 Runtime 已更新」，页脚「已直接发布正式版本」， 但顶栏徽章仍是黄色「待审批 · 已提交，等待管理员通过后影响正式业务」。 用户侧会认为状态与消息通知没及时同步——判断正确，这是前端徽章状态机与后端变更单不同步的 bug，不是「审批设计本身错误」。
层当时实际发生了什么用户看到什么
正式 Runtime PATCH /schema 已写入 apps.page_schema，schema_rev++ 左侧菜单可已变（同会话 React 状态）
变更单 DB 原 pending 单未关闭 —
Composer UI loadChangeQueue 又把旧 pending 挂回 changeId 徽章仍「待审批」
站内信 提交时发给管理员的「改页待审批」可能仍未读 通知与正式发布脱节

2. 正确原则（必须成立）

  1. 本地预览 ≠ 正式业务：对话改页立刻改左侧预览（schemaDirty），默认不写 apps.page_schema。
  2. 草稿绑个人：app_schema_change_requests.author_id = 当前用户。
  3. 正式 Runtime 唯一真相：读路径只读 apps.page_schema + schema_rev；pending 不得冒充正式菜单。
  4. 非管理员不能静默写正式：PATCH /schema → 403 SCHEMA_APPROVAL_REQUIRED。
  5. 管理员两条合法路径：① 审批通过；② 直接发布——二者都必须让 UI 徽章与变更单状态一致。
  6. 预览包（preview-*）走 localStorage，无审批——与正式 /r/{id} 分流正确。

7. 修复要点（3e5c1c5）——确认闭环

直接发布与「待审批」徽章冲突，根因是：正式库已更新，变更单仍 pending。 修复后两条路径在「正式生效」语义上对齐。
  1. 后端 PATCH /schema 成功后调用 supersede_open_changes_after_publish：该应用所有 draft/pending → cancelled。
  2. 通知：相关未读「改页待审批」标已读；作者收到「管理员已直接发布，草稿/待审已关闭」。
  3. 前端：loadChangeQueue 无 open 单时 setChangeId(null)；直接发布后先本地清 pending，再拉列表。
