1一句话结论

现在的问题不是「缺概念」，而是「同一概念在多处重复定义、命名不统一」。

应确立的唯一技术主键 运行时只认 capability_key（如 chat_qa、approval_flow）。 行业、办公、场景、模板、弹幕、首页卡片，都是编排层 UX，最终都要映射到 capability_keys。
当前最大耦合风险 同一数据在 3～4 处静态维护：capability_registry.py、MODULES、CAPABILITIES_SHOWCASE、ROLE_PRESETS、PG Catalog。 改一个能力名，要改多处，容易漂移。
解耦原则（推荐）
  1. SSOT 下沉：能力注册表 + Catalog API 为唯一数据源；前端 showcase / 弹幕 / chip 模板只存「引用 ID」
  2. 编排与运行时分离：Web 负责「选什么」；后端负责「解析成 capability_keys + build_manifest」；Flutter/Web Runtime 只消费 manifest
  3. 营销与产品分离：B2B 原子能力、AI 模板卡片不参与发布管线，不得与 capability 混用同一枚举

2五层模型：从营销到 APK

自上而下，每层只依赖下一层的 ID，不跨层硬编码实现细节。

「模块」一词在代码里有三种含义
  • PromptModule：输入框里的 chip（任意 AgentPick 类型）
  • MODULES 常量：功能模块列表（≈ capability 子集）
  • modules[] 发布字段：带 kind 的已选条目（user/suggest/auto 来源）
建议对外文案统一：chip = 已选条目；功能模块 = capability 的 UX 别名；modules[] = 发布 payload。

4>> 模块选择器：五维分类体系

用户在光球面板（AgentOrbPanel）中浏览的五个维度，类型定义在 agentInputLogic.ts。

export type AgentPick =
  | { type: 'action';     key: string; label: string }
  | { type: 'industry';   key: string; label: string }  // 行业视角
  | { type: 'office';     key: string; label: string }  // 办公分类
  | { type: 'capability'; key: string; label: string }  // 平台能力（showcase）
  | { type: 'module';     key: string; label: string }  // 功能模块（≈ capability）
  | { type: 'scenario';   key: string; label: string }  // 业务场景

推荐与展示顺序

promptSuggest.ts 中 SUGGEST_KIND_ORDER 规定 AI 推荐条分组顺序：

industry → office → capability → module → scenario

五维之间的关系（不是互斥，是不同视角）

维度回答的问题典型 key 示例与 capability 关系
industry 「我是哪个行业的？」 mfg sales med 触发 INDUSTRY_EXTRA 默认模块；筛选行业场景
office 「属于哪类办公域？」 人事行政 流程审批 筛选 96 条办公场景；推荐时分组展示
capability 「平台提供什么产品能力？」 portal creation kb showcase 10 项；部分 key = capability_key
module 「App 里装什么功能积木？」 chat_qa approval_flow key 即 capability_key
scenario 「解决什么业务用例？」 设备报修 请假申请 发布时经 schema_templates 推导 capability_keys
面板默认展示策略（当前实现） 折叠展开后默认只显示：行业(8) + 办公(8) + 平台能力(6)。 用户输入筛选词后才显示场景 / 功能模块 — 避免一次展示过多选项。 见 AgentOrbPanel.tsx 与 FloatingAgentDock.tsx。

英雄区弹幕 = 带 picks[] 的 RolePreset，与 >> 选择器共享同一 AgentPick 类型。

HeroCubeStage → HeroDanmakuCloud → 点击弹幕 → HeroRoleDialog → PromptView.onRoleApply(preset)

RolePreset 数据结构

字段用途示例

role身份标签HR、销售、制造…

弹幕与 >> 面板的分工

弹幕（L4 快捷层）

  • 预设好的「身份 × 场景」故事
  • 降低冷启动成本
  • 数据来自 hero-presets API
  • 点击 = 一键填充，仍可修改

>> 光球面板（L3 编排层）

  • 用户自由组合五维选项
  • 支持搜索筛选
  • 数据来自 Catalog scenarios + MODULES + showcase
  • 多选后显示为 chip
解耦建议：弹幕不应有自己的「模块类型」 弹幕 preset 的 picks[] 应只引用 Catalog 已有 ID（industry key、scenario id、capability key）， 不单独维护一套弹幕专用模块表。

10Web 与 Flutter 的设计解耦

两端不共享 UI 代码，只共享契约（manifest + schema + capability_key）。

Web 创建端 (home/)

职责：编排、推荐、发布、预览

  • AgentInput / AgentOrbPanel — 五维选择
  • PromptView — 发布主流程
  • appAssembly.ts — 组装 bundle
  • api/client.ts — 调 Catalog / Creation API

不依赖 Flutter widget、Dart 路由

后端契约层 (backend/)

职责：解析、生成 manifest、持久化

  • capability_registry.py — 能力 SSOT
  • capability_resolver.py — picks → keys
  • build_manifest.py — keys → pkgs/routes
  • schema_generator.py — page_schema
  • /runtime/{id}/manifest — 运行时读取

两端共同依赖的唯一中间层

Flutter 运行时 (runtime-app/)

职责：按 manifest 渲染已发布 App

  • ConfigService — 拉 tenant config + manifest
  • TenantConfig.resolvedCapabilityKeys
  • capability_manifest.dart — codegen 元数据
  • capability_pages.dart — key → Widget 注册

不依赖 AgentPick、弹幕、B2B 文案

共享契约：codegen 三端同步

单一来源 capability_registry.py，脚本生成：

产物消费方用途
shared/capability-manifest.tshome、scriptsTS 类型 + 能力列表
shared/capability-manifest.jsonCI、文档中性 JSON
runtime-app/lib/data/capability_manifest.dartFlutter中文名、route、flutter_pkg

scripts/codegen-capability-manifest.py

Flutter 解析优先级

tenant_config.dart → resolvedCapabilityKeys：

  1. build_manifest.capability_keys（优先）
  2. page_schema.capability_keys
  3. app.capability_keys（兜底）

当前实现差距（需知晓）

Registry 声明 43 项，Flutter 已实现页面约 4 个 capability_pages.dart 仅注册：shanghai_voice、chat、approval、report。 其余 key 显示 manifest 中文名 +「建设中」— 这是正常的渐进式实现，不是架构缺陷。

  2. 后端发布自动生成 manifest 条目
