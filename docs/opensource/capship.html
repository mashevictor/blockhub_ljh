1. 一句话原则与禁止事项

原则：一切可交付功能都是 Capability。 选型结果只进入 capability_keys → 编译为 page_schema + build_manifest → Web Runtime 与 Flutter Runtime 对称消费。不以「页面硬编码」「只做一端」作为默认实现。
禁止正确做法
只在 home/ 写死一个 Demo 按钮，无注册表条目 先登记 Capability，再挂 Web/App 包
只做 Web Widget，不告知 Flutter 裁剪矩阵 至少：Web 包 + Flutter stub/page，或明确标 web_only/app_only
用场景推荐偷偷塞进未勾选能力 显式 capability_keys 为准；推荐仅作选型前建议
把 LangGraph/RAG 放进交付热路径 它们藏在能力包内部或工作台旁路
宣称「AI 已生成完整能力包」但只产出 JSON 预览 预览页标注 generated；正式能力走标准 Pack 流程

4. 统一对象模型：能力 / Agent / 模块

历史上「模块」「Agent」「场景」「Flutter 工具」命名混用。CapShip 统一为一等公民：Capability。

旧说法CapShip 落点说明
业务模块 / 能力模块Capability.key必须进注册表
Agent（chat_qa / approval…）Capability.agent_id 元数据编排分组用；不单独开第二条交付链
Flutter 工具（扫码/定位）同属 Capability（可 app_only）走同一注册与 manifest
场景 / 行业包选型前的「推荐 keys 集合」不直接写 schema；展开为 keys 再 publish
LangGraph 节点 / RAG能力包内部实现对交付层不可见
 
CapabilityDef {
  key, name, category,
  widget,          // Web 组件注册名
  agent_id,        // 逻辑代理分组（可选元数据）
  web_pkg?,        // 空则约定 @blockhub/web-capability-{slug}
  flutter_pkg?,    // 空则约定 capability_{key}
  route?,          // 空则 /{slug}
  menu_icon?, menu_label?,
  keywords[]
}

5. Web 与 App 解耦约定

flowchart LR M["build_manifest"] --> WP["web_pkgs[]"] M --> FP["flutter_pkgs[]"] M --> Meta["meta.web_template_id
meta.app_ui_id"] WP --> WH["web-core WidgetHost"] Meta --> WL["Web Shell Layout"] WH --> WL FP --> Sync["sync pubspec + registry"] Meta --> Shell["Flutter APP_UI_ID Shell"] Sync --> Shell

Web 侧只认

page_schema + manifest.web_pkgs + web_template_id。禁止读 Flutter 私有类名。

App 侧只认

page_schema + manifest.flutter_pkgs + APP_UI_ID / CAPABILITY_KEYS。禁止依赖 home/。

对称实现最低标准

端必交付物可选
Web packages/web-capability-* + registerWidget 共享包多 widget
App packages/capability_* + CapabilityModule + parity 矩阵 仅 Web 能力时登记说明并文档注明
壳 不改能力包即可换 tabs_portal/bottom_tabs 等 新产品壳先扩模板枚举

6. 已有能力如何实现（标准路径 A）

当注册表已有 key，或新能力按正式包落地时，严格走路径 A。

flowchart TD A1["1. 定 key / name / category"] --> A2["2. 写入 capability_registry.py"] A2 --> A3["3. 建 Web 包或复用 web_pkg"] A2 --> A4["4. 建 Flutter 包或复用 flutter_pkg"] A3 --> A5["5. registerWidget + 路由页面"] A4 --> A6["6. CapabilityModule + parity-matrix"] A5 --> A7["7. 本地 publish 冒烟"] A6 --> A7 A7 --> A8["8. Web 打开 + APK 裁剪日志含该 pkg"]

步骤详情

  1. 定 key：小写+下划线，稳定不改；例 inventory_scan。
  2. 注册：backend/app/data/capability_registry.py 增加 CapabilityDef；约定足够时不必填 web_pkg/route。
  3. Web 包：packages/web-capability-{slug}/ → registerWidget('XxxWidget', ...)；由 runtime-web 按 manifest 懒加载。
  4. Flutter 包：packages/capability_{key}/ 实现模块；更新 shared/flutter-parity-matrix.json；构建脚本 sync pubspec。
  5. 禁止在 runtime-web/App.tsx 或 home 硬编码特殊分支（除非壳级全局行为）。
  6. 业务落地：正式包须接真 API + DB（鉴权、租户）；禁止 localStorage / 内存假数据冒充业务。参考 approvals、device_repair。
  7. 验收：仅勾选该能力 publish → schema.menu 含路由 → Web/App 读写同一接口且刷新仍在 → APK build log 含对应 flutter_pkgs。
Agent / RAG / 语音链路：全部写在能力包内部（如 capability_shanghai_voice），对外只暴露 Capability 边界。路径 A 生产包不允许用 mock 冒充已交付。

7. 用户要的能力暂时没有时如何做（路径 B → A）

flowchart TD B0["用户选型出现未知 key
或不在注册表"] --> B1["Resolver: dropped / pending_codegen_keys"] B1 --> B2["已知 keys 仍完整交付 Web/App"] B1 --> B3["异步 Codegen Job"] B3 --> B4["LLM 生成 generated_page JSON"] B4 --> B5["merge 进 page_schema"] B5 --> B6["Web GeneratedPageWidget 预览"] B6 --> B7{"业务是否要转正?"} B7 -->|否| B8["保持预览 + 产品说明"] B7 -->|是| A["走路径 A：正式 Capability Pack"]
阶段交付物用户感知工程状态
B1 降级 已知能力正常 Web/APK 提示「部分能力生成中/未支持」 pending_codegen_keys
B2 预览 type: generated_page 节点 可打开占位/说明页 不是完整 Dart/TS 包
A 转正 注册表 + 双端包 与一等能力无差别 唯一生产可用形态
口径红线：路径 B 只能说「预览 / 占位 / AI 草图」，不能说「已生成完整 App 能力包」。转正必须走路径 A。

9. 契约字段与壳矩阵

Publish 输入

{
  "capability_keys": ["chat_qa", "approval_flow"],
  "web_template_id": "tabs_portal",
  "app_ui_id": "bottom_tabs",
  "deliver": "both"

编译输出

  • page_schema — 菜单、组件树、theme.templateId
  • build_manifest — web_pkgs / flutter_pkgs / routes / meta
  • android_app_id — 每应用唯一包名

App 壳 app_ui_id

id语义

10. 开发检查清单（每个能力必勾）

  • key 已写入 capability_registry.py（或明确走路径 B 且有 pending 说明）
  • Web：widget 可注册；manifest.web_pkgs 能加载
  • App：flutter 包或显式 app_only；parity 矩阵更新
  • 未在 home/runtime 写能力特例分支（壳级除外）
  • 显式 keys 不会被场景推荐污染
  • publish 后 schema.menu / routes 可见
  • deliver 含 app 时构建指纹含该 key；包名独立
  • 若用了 LLM/RAG/语音：仅在能力包内，文档注明
  • 路径 B 文案未夸大为「完整生成」
  • 更新相关 docs / 本 HTML 若改了约定

12. 对话改页与 Schema 审批（平台编排）

定位：这是 CapShip 开源核心能力之一（Composer + Runtime 写回门禁）， 不是路径 A 的业务 capability_key。 禁止注册为 compose_edit / schema_change 假模块并挂进 capability_keys。

Composer 三模式：live_edit（对话改页，默认）· module_flow（数据流）· select_modules（选模块）。产品首页「对话改页」创建入口与 Runtime Dock 对齐。

状态机

对话改页 → 本地预览 (schemaDirty，正式 schema 不变)
     ↓ 保存草稿
  draft (绑 author_id) ──取消→ cancelled
     ↓ 提交审批
  pending ──管理员──┐
     ↓ 通过          ↓ 驳回
  approved         rejected
     ↓
  正式 page_schema + schema_rev++ + app_schema_revisions

参考 API

方法路径作用
POST/api/v1/creation/compose-editLLM 产出改页 ops
POST/api/v1/runtime/{id}/schema/changes保存个人草稿
POST.../schema/changes/submit提交审批
POST.../changes/{id}/approve管理员通过并写入正式 Schema
边界与序列图见 capship-scope-boundary.html §4.2。 实现包：@capship/composer（平台包，非 web-capability-*）。
